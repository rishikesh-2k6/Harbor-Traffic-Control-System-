## Problem

## Required implementation

2. Move crash notifications, warnings, and relevant system status messages into a dedicated side panel, status sidebar, or clearly separated notification region.
3. Ensure notifications never obscure the central 3D simulation viewport.

- The main simulation remains unobstructed.
- Error details are actionable and visible.
- Recoverable failures do not unnecessarily terminate the entire application.

# PHASE 5 — IMPLEMENT PREDICTION LOGGING AND GROUND-TRUTH VALIDATION

## Problem

The simulation produces predictions, but we need a systematic way to determine whether those predictions are correct.

We need to record predictions such as:

- Vessel class
- Vessel displacement/weight
- Vessel speed
- Vessel direction
- Other existing model outputs that can be validated

We must be able to compare these predictions against the actual simulated values.

**This is a core functional requirement, not just a dashboard enhancement.**

## Step 1: Audit the existing prediction pipeline

Inspect `mlmodel.py`, `simulator.py`, `traffic_algo.py`, and related modules.

Determine which models actually predict which variables.

For example:

- If the existing VesselMLP predicts vessel class and displacement, log those predictions.
- If speed and direction are calculated by the simulation rather than predicted by a trained model, record them as simulation estimates or controller outputs instead of falsely attributing them to ML.
- If speed and direction prediction models do not exist, implement them only if the current project requirements, available training data, and architecture support a defensible solution.

Do not label a ground-truth value as a prediction.

## Step 2: Create a structured prediction record

Design a reusable prediction logging interface.

Each record should contain, where applicable:

- Unique prediction ID
- Simulation run ID
- Timestamp or simulation frame
- Vessel ID
- Prediction source/model name
- Model version or artifact identifier
- Prediction task
- Predicted value
- Actual ground-truth value
- Error or correctness result
- Validation status
- Environmental scenario: normal or monsoon
- Relevant confidence score, if the model provides one
- Relevant metadata required for debugging

For a multi-output prediction, store individual outputs in a clear, queryable structure.

Do not log sensitive or unnecessary information.

## Step 3: Establish reliable ground truth

Use the authoritative state maintained by the simulation as the ground truth.

Examples:

| Prediction | Ground-truth source | Validation |
|---|---|---|
| Vessel class | Actual vessel class configured in the simulator | Exact match / accuracy |
| Displacement or weight | Actual simulated displacement in consistent units | Absolute error, MAE and RMSE |
| Speed | Actual simulated vessel speed at the corresponding timestamp | Absolute error, MAE and RMSE |
| Direction | Actual simulated heading/direction | Angular error with circular wraparound |
| Other continuous output | Corresponding authoritative simulator state | Task-appropriate error metric |

Important rules:

1. Match predictions to the correct vessel and simulation frame.
2. Use consistent units throughout.
3. Compare values from the same simulated time, or explicitly account for prediction horizon.
4. Do not compare predictions against values that have already been overwritten by later simulation updates.
5. Separate unavailable ground truth from an incorrect prediction.
6. If a field is not actually predicted by any model, mark it as not applicable rather than inventing a model result.

For direction, account for the circular nature of angles. For example, predictions of 359° and 1° differ by 2°, not 358°.

## Step 4: Create a persistent prediction log

Use a suitable persistent format such as SQLite or CSV, depending on the current architecture and query requirements.

Prefer a design that can support:

- Multiple simulation runs
- Historical comparisons
- Filtering by vessel, model, scenario, and time
- Exporting results for reports
- Restarting the application without losing earlier records

If using SQLite, design sensible tables, indexes, unique identifiers, and transactions.

If CSV is sufficient for the existing scale, document its limitations and ensure records are written safely.

Do not rewrite the entire telemetry storage architecture unnecessarily.

## Step 5: Build the prediction validation engine

Create a modular component that:

1. Receives the prediction record.
2. Retrieves the corresponding ground-truth state.
3. Computes the appropriate error or correctness metric.
4. Stores the validation result.
5. Updates aggregate statistics.
6. Exposes the results to the UI and reporting layer.

Support, as applicable:

**Classification**
- Correct/incorrect
- Accuracy
- Per-class precision, recall, and F1 score when enough labeled observations exist

**Regression**
- Absolute error
- Mean Absolute Error (MAE)
- Root Mean Squared Error (RMSE)
- Mean Absolute Percentage Error only when mathematically appropriate and the target values make it meaningful

**Direction**
- Circular angular error

Clearly distinguish per-prediction correctness from aggregate model performance.

Do not present a model as accurate merely because a few predictions matched.

## Step 6: Add validation metrics to the dashboard

Display useful metrics such as:

- Total predictions
- Number validated
- Correct classification count
- Classification accuracy
- MAE/RMSE for applicable regression outputs
- Recent prediction history
- Predicted versus actual values
- Error trends over time
- Normal versus monsoon performance
- Per-model or per-task metrics

Include a prediction history table, with filters where practical.

Example:

| Vessel | Task | Predicted | Actual | Error/Result |
|---|---|---|---|---|
| V-001 | Class | Cargo | Cargo | Correct |
| V-002 | Weight | 12,400 kg | 12,000 kg | 400 kg |
| V-003 | Speed | 8.2 kn | 9.0 kn | 0.8 kn |
| V-004 | Direction | 359° | 1° | 2° angular error |

These values are illustrative only. The running system must display real results from the simulator.

Provide a detail view for individual records when useful.

### Acceptance criteria

- Every supported prediction is logged with a unique identifier.
- The prediction is matched to the correct ground truth.
- Validation occurs automatically during simulation.
- The system persists records across application restarts.
- Users can distinguish validated, incorrect, unavailable, and pending results.
- Aggregate metrics are calculated from actual logged observations.
- The dashboard does not fabricate validation metrics.

# PHASE 6 — BUILD A MODEL OR EVALUATION PIPELINE THAT CHECKS PREDICTIONS AGAINST REAL SIMULATION VALUES

## Objective

Provide a defensible way to evaluate whether our prediction models perform well against the actual simulated system.

Do not confuse an evaluation mechanism with a second predictive model.

### A. First implement a ground-truth evaluation baseline

Use the simulation's authoritative state to create a reliable evaluation pipeline.

For every supported prediction task:

1. Capture the model input.
2. Capture the model prediction.
3. Capture the matching ground-truth value.
4. Compute the appropriate metric.
5. Save the result.
6. Aggregate performance by task, model, vessel class, and environmental scenario.

### B. Audit existing trained models

Inspect:

- Model architecture
- Training procedure
- Training dataset
- Feature definitions
- Feature scaler
- Label encoder
- Saved model weights
- Inference pipeline
- Model loading and preprocessing
- Existing train/test splits
- Existing evaluation metrics

Ensure the model receives the same feature order and preprocessing during inference as it did during training.

### C. Determine whether additional predictive models are necessary

If speed and direction are intended to be predicted but no suitable trained models exist:

1. Assess whether historical or generated labeled training data is available.
2. Define the prediction target and prediction horizon.
3. Prevent data leakage.
4. Split training, validation, and test data appropriately.
5. Establish a simple baseline before introducing a more complex model.
6. Train and evaluate a suitable model only if justified by the data.
7. Save model artifacts and preprocessing requirements.
8. Compare the new model against the baseline on held-out data.
9. Integrate inference into the existing architecture only after the model passes validation.

Do not use current ground truth as an input feature if doing so leaks the answer into the prediction.

Do not train and evaluate on the same observations and then claim the resulting score demonstrates generalization.

### D. Prevent misleading evaluation

The simulation is a source of ground truth, but the model must not automatically receive perfect scores simply because the simulator knows the actual answer.

Keep the roles separate:

`Simulation state → Ground truth`

`Available sensor/features → Model prediction`

`Prediction + matching ground truth → Evaluation`

Where appropriate, use time-separated observations and realistic noise or missing data.

Clearly label results as simulation-based evaluation. Do not imply that simulated performance proves real-world maritime deployment readiness.

### E. Evaluate normal and monsoon conditions separately

Produce separate performance reports for normal and monsoon scenarios.

Check whether increased acoustic noise, missing sensor readings, drifting sensors, and communication delays affect:

- Prediction quality
- Availability of model inputs
- Number of predictions produced
- Validation coverage
- Error rates
- End-to-end detection latency

Distinguish model prediction errors from missing data, delayed packets, and unavailable communication links.

### Acceptance criteria

- Existing models have a reproducible evaluation procedure.
- Predictions can be compared against authoritative ground truth.
- Metrics are computed from held-out data when assessing model generalization.
- Normal and monsoon results can be compared independently.
- Unsupported predictions are clearly identified.
- No artificial accuracy improvements or fabricated results are introduced.
